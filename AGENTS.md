# Site Agent Contributor Guide

This repository is a small, single-instance-at-runtime Python service. Keep
changes easy to trace from an HTTP request or scheduled job to a persisted
state change.

## Mission Lock: Ada Designs the Site

The product mission is not to help an engineer hand-build a design. The mission
is this autonomous owner journey:

1. A person completes and confirms the intake.
2. Ada consumes that confirmed intake, its assets, copy, constraints, and
   experience plan.
3. Ada carries the work through the defined design pipeline herself.
4. About 20 minutes later, the person receives a complete candidate in the
   Design review flow.
5. Production remains unchanged until the person explicitly approves it.

The generated site is Ada's output. Do not manually redesign, rewrite, or polish
a candidate in application-development work to make a run look successful. A
manual repair that bypasses Ada proves neither the product nor the pipeline.

The confirmed experience plan is an executable product requirement, not
decorative metadata. If it specifies an adventure path, signature interaction,
motion system, narrative sequence, or other defining experience, that behavior
must be visibly present in Ada's generated candidate and must work in the actual
Design-tab preview. Source code, a manifest entry, a model claim, or an internal
gate marked `passed` is not evidence that the experience was delivered.

Before changing code, state the current pipeline failure in this form:

`confirmed intake -> Ada planning -> Ada generation -> build -> deterministic validation -> visual/behavioral review -> owner review`

Name the first broken boundary and fix only what prevents Ada from crossing it.
Then rerun Ada from the confirmed intake (or the earliest valid persisted
boundary). Do not substitute your own implementation for the rerun.

For design-pipeline work, success requires all of the following:

- the candidate was generated by Ada from the confirmed intake;
- the defining experience-plan behaviors are observable, not merely present in
  source;
- generated JavaScript hydrates in the same preview URL and sandbox the owner
  uses;
- required motion and interactions are exercised at representative viewports,
  including reduced-motion behavior;
- browser console errors, failed module requests, and failed asset requests are
  treated as failures;
- visual review evaluates the actual owner-visible candidate after hydration;
- the elapsed autonomous path is compatible with the approximately 20-minute
  product promise;
- no production mutation occurs without explicit owner approval.

If these conditions are not proven, report the run as incomplete or blocked.
Never describe infrastructure progress, passing unit tests, generated GSAP code,
or a visually attractive static page as completion of the product mission.

At the start and end of every design-pipeline task, answer these questions:

1. Did Ada—not the coding agent—create the candidate from the intake?
2. Did the candidate visibly follow the defining experience/adventure path?
3. Was that behavior observed in the real owner review surface?
4. Did any workaround bypass the autonomous pipeline?
5. Is the result honestly ready for owner feedback within the intended journey?

Any `no` means the mission is not complete.

For the authoritative corrective architecture and the failure analysis that
motivates it, follow
`docs/brand-composition-and-behavior-system-implementation-plan.md`. Do not use
an older overlapping plan to weaken its experience-journey, integrated
realization, autonomous repair, or end-to-end acceptance requirements.

## Invariants

- A site mutation is either an explicit owner action or a pending draft.
- A pending visual build is reviewed in the Design tab; do not add raw preview
  links as a substitute for the review flow.
- Production is changed only by an explicit approval operation.
- Chat jobs are durable. A job may disappear from the active-jobs list after it
  finishes, but it must remain inspectable by its ID and conversation.
- Preview URLs must work under the deployment mount point, currently `/ada/`.
- Site-specific assumptions belong in instance configuration, not generic
  validation or service code.
- Plugins and MCP providers must call application services and contracts. They
  must not call route functions or access `Memory.conn` directly.
- Owner dashboards are functional workspaces: no marketing hero/H1 occupying
  chat/preview space. Simplification must retain visible Growth, analytics,
  SEO, research, reports and activity; reveal details progressively.
- HelloAda connection changes must follow `docs/helloada-connection-contract.md`.
  Never claim a customer release ready from a public health response or local
  fixture: verify the correct tenant in an authenticated production session.
- New-site onboarding follows `docs/helloada-project-selector-to-payload-intake-contract.md`:
  HelloAda is only the multi-project selector/create entry; Site-Agent prepares
  the canonical Payload workspace, and the owner is handed into that admin
  before Ada intake or design begins. The older Intake Lab journey plan is
  superseded for UI topology; it must not be used to reintroduce a second
  owner-facing intake/design surface.

forward destination. Automatic activation requires Cloudflare and Payload to
both confirm the same mailbox. Email Routing is not a general-purpose mailbox
or unrestricted Gmail replacement.

Email provisioning uses distinct protected `cloudflare_dns` and
`cloudflare_email` credential profiles. The former requires Zone Read, DNS
Read and DNS Write; the latter requires Email Routing Rules Read/Edit and Zone
Settings Read/Edit on managed zones plus Email Sending Edit on the owning
account. Do not reuse the general Worker-management token for Email Service
calls or merge these scopes.
For a tenant without a custom website domain, a read-only plan may specify an
explicit host-owned email domain and unique local part with `--email-domain`
and `--local-part`; `--apply` persists those values to that registered tenant.
The current implementation supports zone-apex email domains only. Do not use
Cloudflare's deprecated Email Routing subdomain DNS query as a fallback.

### No parallel architecture or silent recovery path

- Every managed or publishable new site starts from
  `src/site_agent/templates/next-payload` and imports the version-pinned shared
  Payload admin/core packages. The isolated blank toolchain is an experiment
  only; it cannot be adopted, provisioned, or deployed as a customer site.
- Payload is the sole content/schema authority. Do not add customer-local
  collection/global definitions, duplicate content JSON, static-site engines,
  remote-vs-local readers, source-ID-as-relation behavior, or alternate CMS/API
  paths. Data transformations must be explicit operator-run migrations into
  the shared Payload contract; runtime content conversion is not supported.
- Runtime reads and writes are fail-closed. Missing required documents, media,
  configuration, bindings, locale data, package identity, or tenant identity
  produce an explicit error; they must not switch to JSX copy, static files,
  another endpoint, another credential, an empty success result, or a second
  schema. Optional content is omitted only when the canonical schema declares
  it optional.
- The shared API's `workspace_api.tenants` map stays empty. Every persistent
  tenant, existing or newly spawned, is loaded from the single protected
  `provisioned_root/tenants.json` registry and its per-tenant `tenant.env`.
  Never add a tenant-specific systemd `EnvironmentFile` or a second static
  tenant list; migrate old host declarations with
  `scripts/migrate-static-tenants-to-registry.py`.
- A production Worker reads tenant secrets only from its Cloudflare runtime
  bindings. Process variables are a local-development/test source only. Payload
  CLI execution is explicit through package scripts; production CLI operations
  require Cloudflare credentials and have no local-D1 override.
- There is no legacy static-site engine, article file publisher, or parallel CMS
  route. Website pages and articles use the shared Payload schema and the
  canonical Next.js/React build profile only.
- Pelican is retired: do not restore a dependency, build profile, scaffold,
  importer, journal API, static article publisher, or compatibility branch.
  Historical plan documents are archival context, not executable guidance.
- Deployment never runs `payload migrate:create` or guesses SQL. A new-site
  bootstrap request may apply the exact committed scaffold migration chain only
  after the registered tenant D1 is proven empty. An existing-tenant schema
  migration must be an explicit release-queue request naming the exact prior
  ledger identity and registered target head. The pipeline verifies the live
  ledger is that exact strict prefix of the candidate's committed chain, uploads
  the candidate without promoting it, applies only the committed migration,
  verifies the full target ledger and Payload contract, then promotes that exact
  uploaded version. Ordinary Worker releases never apply migrations; any
  mismatch, missing ledger, unrecognized prefix, or unrequested schema change
  fails closed. No migration generation or SQL guessing occurs in deployment.
- Bootstrap and source promotion must use the one canonical VPS release queue.
  They may not call Wrangler/OpenNext production deployment directly or replace
  an existing tenant checkout to “repair” its baseline. A mismatched or
  untracked baseline stops with an operator-visible diagnostic.
- New-site bootstrap provisions and durably records the Cloudflare Worker
  identity before queueing its first version. `wrangler versions upload` only
  uploads versions for an existing Worker; it does not create the Worker
  resource. Use the idempotent Cloudflare resource provisioner and the same
  version-upload/verified-promotion pipeline used for later releases. Do not
  seed a placeholder Worker or bypass the VPS release queue with a first-deploy
  `wrangler deploy` path. A workers.dev origin must be built from the account's
  Workers subdomain returned by Cloudflare, never guessed as
  `<worker>.workers.dev`. The canonical release enables that script's
  workers.dev route only after the exact version is promoted and before live
  health/connection verification; a custom-domain release does not change the
  workers.dev route. Keep generated Worker script names at or below Cloudflare's
  54-character limit when the workers.dev preview route is enabled; long tenant
  IDs must be shortened deterministically with a tenant-specific hash, while
  already-valid resource names stay stable.
- Shared Python API releases use `deploy/desired-api-release.json` and the same
  VPS release timer. Queue one new release ID plus the full official `main` SHA;
  the VPS tests that exact source, builds and smoke-checks one wheel, checks its
  runtime dependencies against the service environment, installs it into an
  immutable release slot, then restarts and checks `/healthz`. The current slot
  changes atomically and a failed health gate restores the prior slot. Never
  `pip install` from a checkout, `git pull` the running `/SOCIAL/site-agent`,
  restart the API by hand, or deploy a moving branch. The current source checkout
  may be dirty and is not the API release artifact.
- HelloAda's project-selector Worker is also released through that one VPS
  dispatcher, using `deploy/desired-helloada-app-release.json` with a unique ID
  and exact full SHA on `weareheadless/helloada/main`. It must pass the pinned
  Node/npm checks, tests, lint, typecheck, Next build and local-binding OpenNext
  build before the dispatcher uploads and promotes the exact Worker version.
  `/api/health` must report the same SHA after promotion or the pipeline restores
  the exact prior Worker version. The owner-handoff private key is read only from
  the protected mode-`0600` VPS secret file and injected only into the Worker
  upload; it must never enter Git, build processes, logs, browser bundles or
  chat. No direct Wrangler release, manual Worker upload, or separate release
  path is permitted. The release token requires Workers Routes Write scoped only
  to zones managed by Site-Agent. If an atomic Durable Object deployment has an
  ambiguous CLI outcome, use only the canonical reconciliation evidence path:
  preserve the failed receipt, prove the exact live version and namespace, then
  queue a fresh unique canary release. Lifecycle proof is not a canary pass.
  See `deploy/README.md` for queue, permission and receipt procedure.
- The VPS release service executes only
  `/SOCIAL/payload-releases/bin/current/dispatch-payload-releases.py`. The dispatcher
  fetches official `site-agent/main`, snapshots its exact full SHA, and runs the
  reconciler from that immutable snapshot. It synchronizes only its own reviewed
  dispatcher into a versioned slot; it never installs host units or runs `sudo`.
  The release service keeps `NoNewPrivileges=true`, because it builds customer
  code. API promotion requests a restart only for the fixed
  `site-agent-api.service` through the root-owned, fixed-function socket broker
  installed by the reviewed host bootstrap. The broker accepts no command or
  unit arguments. The bootstrap installs systemd units and broker from the exact
  official-main snapshot and removes the exact obsolete Polkit rule path. If a
  host unit changes, run that bootstrap explicitly; never let a tenant build or
  routine release rewrite host policy. Never point systemd at
  `/SOCIAL/site-agent/scripts` or any mutable checkout.

## Module Ownership

- `config.py`: config loading, validation, secret resolution.
- `core/memory.py`: SQLite persistence and migrations.
- `core/chat_jobs.py`: durable owner-message execution only.
- `core/scheduler.py`: schedule calculation and execution only.
- `brain/`: decisions, prompts, and tool-loop policy.
- `hands/`: external systems and repository mutations.
- `web/server.py`: HTTP/session translation; keep business workflows out of
  route handlers when extracting or changing them.
- `web/preview.py`: staged output builds, preview URL rewriting, and preview
  cache only.
- `web/static/`: current no-build admin UI. Keep Design state transitions
  explicit and do not introduce a framework for small fixes.

## Debugging Workflow

For a design request, follow this chain in order:

1. `GET /api/chat/jobs/{job_id}`: confirm queued, running, done, or error.
2. For a completed result, read `result.merge_draft_id` or `result.proposal_id`.
3. `GET /api/drafts`: confirm the referenced draft is pending.
4. `GET /api/pages?draft_id={draft_id}`: confirm the Design page list.
5. Load the iframe through `/ada/api/review/{draft_id}/{page}` and inspect
   every CSS/image request under the same `/ada` prefix.
7. Approve or decline only from the Design controls.

Do not infer completion from `GET /api/chat/jobs`; that endpoint intentionally
returns active jobs only.

## Change Rules

- Start with a failing focused test or a reproducible API request.
- Prefer one behavior-preserving extraction over a rewrite.
- Prompts carry contracts, typed shapes, and behavioral rules only. Never embed
  worked conversational examples, sample replies, sample questions, or canned
  phrasings in model prompts: models imitate them — language, tone, and content —
  instead of answering from the owner's own context. This is a standing invariant,
  not a style choice. The model mirrors the owner's language, tone, and business
  context from the conversation itself; the host never detects, classifies, or
  injects language. Host-side conversation heuristics (message-kind detection,
  "nudge" retries, restatement rules) are scaffolding that traps the model and
  must not replace the model's own conversational judgment.
- Keep public API paths stable while moving business logic behind them.
- Use typed result objects or documented dictionaries at new boundaries.
- Include job, draft, conversation, provider, or adapter IDs in diagnostics.
- Never commit credentials, databases, caches, worktrees, screenshots, or
  generated OpenCode configuration.
- Run the focused tests first, then the full suite and package smoke test.

## Extension Rules

The supported extension direction is:

`HTTP/MCP adapter -> application service -> typed contract -> adapter/provider`

New integrations should first implement a narrow capability contract. Do not
add automatic Python module loading or a universal plugin base class until a
real external integration requires it. Any external mutation must create a
draft or use an explicit owner-approved service.

## Source-control and deployment connection

Use `/SOCIAL/configs/host-credentials.yaml` as the non-secret source of truth
for GitHub and Cloudflare connection wiring. It contains protected-file paths,
environment-variable names, and the GitHub SSH identity path; it never contains
credential values. Resolve credentials through `site_agent.credentials` or the
protected environment files at runtime. Never copy tokens, account secrets, or
credential-file contents into this repository, `AGENTS.md`, prompts, logs, or
commits.

Before pushing code:

1. Confirm the intended repository URL and branch explicitly. This checkout
   uses `git@github.com:weareheadless/site-agent.git` with `main` as the
   upstream branch. Never infer a destination from a tenant's website
   repository; stop if the remote is absent or differs from that target.
2. Inspect `git status`, `git diff`, and `git log --oneline -10`.
3. Run the relevant tests and compile checks.
4. Commit only source, tests, and safe documentation; exclude `.env` files,
   databases, generated output, and deployment credentials.
5. Push the reviewed commit with the credential that has access to the explicit
   remote (prefer the configured SSH identity; use a protected credential
   helper for token-only accounts, never a token-bearing URL) and report the
   commit and remote branch.

For Cloudflare checks, load the protected environment selected by the host
credential profile and use a read-only identity command such as `wrangler
whoami` before any deployment. Deployment remains a separate, explicit action
from a Git push.

## Tenant deployment handoff

Each tenant's frontend or Payload application is a separate repository named by
the central tenant manifest. The VPS-owned Payload release pipeline in
`deploy/payload-customers.json` and
`scripts/deploy-payload-customer.py` owns production promotion for every
tenant. A local site-agent change, a customer-repository push, or a direct
`wrangler deploy` is not a deployment.

### Mandatory Payload/Worker release pipeline

Commit the approved tenant's full 40-character customer SHA and a new release ID
to `deploy/desired-releases.json` on the official `main` branch. The VPS
`helloada-release.timer` polls that file through the configured GitHub SSH
identity every minute. `helloada-release.service` snapshots the exact control
commit and runs `scripts/deploy-payload-customer.py` from that snapshot. Full
operating and installation instructions are in `deploy/README.md`.

The queue operation determines the required Payload gate. An exact
`initializeSchema` request is passed as `--release-purpose workspace-bootstrap`:
it proves the committed schema/migration identity and the live authenticated
workspace contract, but it does not require or publish business content. Every
other queued site release is passed as `--release-purpose website` and runs the
canonical Payload verifier. The release manifest must explicitly declare
`websitePresent`: false allows an intentionally empty intake site after all
schema/draft/version/media/global reads pass; true additionally requires the
published business identity, shared navigation and complete homepage. Never
infer the flag from missing content or relax the verifier for a failed check.
After exact live health and 100% promotion, every Worker release must use the
authenticated `activate-runtime` handoff to pin that receipt's Payload
identity and website state into the central tenant config before the
authenticated API connection check. API release preflight compares each
tenant config to its currently active Worker's health identity, not a queued
candidate manifest. See `deploy/README.md` for the full contract.

The same release gate owns Cloudflare's non-versioned Queue consumer
registrations. It must attach and read back the exact Messages and
dead-letter consumers declared in the candidate's `wrangler.jsonc`, scoped to
the registered tenant Worker and Queue IDs. A healthy Worker or successful
version promotion is not proof that the message pipeline is active. Fail the
release on missing, ambiguous, or unrelated consumer registrations; do not
repair them manually in Cloudflare or with ad-hoc Wrangler commands.

The central script is a hard gate, not a repair or fallback layer. It must:

1. resolve the tenant from the manifest and reject an unregistered target;
2. clone the configured repository into an isolated temporary workspace under
   `/SOCIAL/payload-releases/work`, verify the immutable SHA is on official
   `main`, and use a detached checkout;
3. resolve Cloudflare through `/SOCIAL/configs/host-credentials.yaml` using
   `site_agent.credentials`, never by sourcing `/SOCIAL/site-agent/.env`;
4. verify the exact Node/npm versions from the release manifest, then run
   `npm ci`, typecheck and the full OpenNext build with isolated local bindings
   and no production credentials;
5. inspect the generated `.open-next` artifact and reject legacy `/api/atelier`
   source, missing Growth contract markers, or stale Payload admin markers;
6. resolve the tenant's registered runtime secrets and attach them to the
   exact candidate through a private, mode-`0600`, short-lived `--secrets-file`
   passed through OpenNext `upload`; remove that file immediately after upload,
   promote that immutable version, then verify that exact version receives 100%
   of traffic, check the live source SHA, and perform the authenticated
   Ada/Payload connection gate; and
7. persist a secret-free receipt in `/SOCIAL/payload-releases/runs`. Build
   checkouts, `node_modules`, caches and OpenNext output exist only in the
   isolated workspace while the release runs. The runner removes that workspace
   after success or failure; the next locked queue poll removes any workspace
   left by an interrupted systemd job. The receipt retains the exact Git SHA,
   per-file artifact hashes, uploaded Cloudflare version and deployment
   identity; GitHub and Cloudflare are the durable source/artifact stores.
   Never mutate Worker secrets after promotion through Cloudflare's
   script-secrets endpoint or `wrangler secret put`: those operations create a
   different version, and `wrangler secret put` deploys it immediately,
   invalidating the exact-version release receipt. Failed or interrupted
   releases stop. Fix their cause and commit a new release ID to retry; never
   repeat failed builds automatically or bypass their gate.

The shared site-agent preview builder uses the same explicit toolchain policy.
The API root config's `source_deployment` section must specify `node_path`,
`node_version`, `npm_command`, and `npm_version`; `TenantRegistry` carries that
policy into every declared and newly registered tenant. Both versions are
checked before a preview build. Missing configuration, an unavailable
executable, or a version mismatch is a hard failure; never fall back to the
machine's system `PATH` or a shell-installed Node/npm.

For a promoted version whose live gate failed during rollout, the documented
`--verify-only` command may repeat the exact read-only checks under the queue
lock without rebuilding or deploying. It validates the receipt's artifact-hash
manifest and resolves the active 100%-traffic version directly from Cloudflare.
During adoption only, a Cloudflare secret-triggered version is accepted when
its code and non-secret binding identity exactly match the uploaded version;
the verifier rechecks the active deployment around live health and authenticated
connection checks. The control-plane activation receives that verifier proof and
validates it against the canonical release identity; it does not require a
temporary `running` receipt. Failed read-only verification does not rewrite the
canonical promotion receipt. It requires no local checkout or archived build.
Never edit a failed receipt into success by hand.

There is no customer-facing legacy admin API. The canonical Payload bridge is
`/api/helloada/*`; customer source containing `/api/atelier` is rejected. The
Python/FastAPI service remains the internal shared API only where an application
contract explicitly requires it; it is not an alternative customer admin
surface, deployment path, or fallback.

GitHub CI success and a public health response are not sufficient live
verification. After a passing receipt, reload a fresh authenticated browser
document with a cache-busting release query and verify the changed UI and
connection behavior. Do not report a release as live until this check passes.

### Host credential source of truth

The non-secret GitHub/Cloudflare wiring is defined once in
`/SOCIAL/configs/host-credentials.yaml`. Package defaults load that file through
`credentials.profile_file`, so every tenant inherits the same host profile. Do
not copy credential blocks into tenant configs unless an intentionally isolated
deployment is being created.

The profile names protected host resources and environment variables without
storing their values. `site_agent.credentials` is the only resolver for these
profiles. Check readiness through the resolved profile, never by rediscovering
keys or tokens per website. A safe Cloudflare check is:

```bash
npx wrangler whoami
```

Never print, paste, commit, or pass credential values to Ada/model prompts.

- Backend/API changes: validate here, then queue a full-SHA API release through the central release pipeline; never restart the service by hand.
- Every managed Payload gateway uses exactly `/api/workspace`. Keep this path explicit in defaults and tenant provisioning, reject any other runtime route, and migrate existing registered host configs with `scripts/migrate_payload_gateway_prefix.py` before releasing that strict API contract. Never probe or fall back to another route.
- Frontend/Payload changes: validate and push the tenant's configured repository,
  then promote only by committing its SHA to the central release queue.
- Never commit protected credential files, tenant memory databases, or generated
  Worker/build output.
- Keep the packaged intake defaults stable; database-only intake/research must
  never trigger a design build or production publish.


## Shared runtime ownership and customer fan-out

- src/site_agent/templates/next-payload plus the declared deploy/shared-runtime-overlay.json boundary is the source of truth for code shared by tenant Workers. Tenant repositories own approved site design, content, migration history and domain routes; the release runner overlays the shared runtime into a disposable build workspace and never rewrites those repositories.
- A central runtime change is identified by shared_runtime_fingerprint. The fingerprint covers the overlay contract, exact central runtime files, package pins and the complete packages/helloada-mailflare build source. If a runtime input changes, the VPS timer records a new, immutable fan-out release in deploy/desired-releases.json.
- Runtime rollout is canary-first and bounded: the registered canary must pass the normal build, Cloudflare deployment and live-health gates before automatic tenants are released in batches of five. New tenants are enrolled as automatic; the first release already includes the current runtime. Existing one-off test workspaces can explicitly remain manual.
- Each fan-out request uses that tenant’s last successfully deployed full source SHA and a unique release ID. It does not inspect, modify, commit or push a tenant repository. The tenant still receives its own generated Worker artifact because its site design/content is bundled into that Worker; builds and promotions are automated by the single VPS queue.
- The queue pins the requested runtime fingerprint, the build rejects a mismatch, and the receipt records both tenant source SHA and shared-runtime fingerprint. Pending requests are never overwritten, failed/interrupted IDs are never retried, and failed canaries hold the automatic rollout until the failure is addressed.
- Do not use customer-specific Wrangler commands or ad-hoc repo commits to propagate common code. The only customer release path is the GitHub desired-release queue processed by helloada-release.timer; inspect its per-tenant receipt and journal on failure.
- A deployed receipt and health check do not prove the customer-visible UI. Use a fresh authenticated browser document for user-facing verification before reporting the experience as verified.

## Durable Object lifecycle release boundary

The first Worker version that introduces an unapplied Durable Object migration for a tenant must use the explicit atomic lifecycle path in `scripts/deploy-payload-customer.py`. Do not upload that candidate as a version and do not add an automatic deploy fallback. The runner applies the exact Payload migration/verifier gates before atomic deployment, supplies the same secrets/vars/SHA/tag as an ordinary release, persists the lifecycle identity/state in the tenant receipt, and verifies a new Cloudflare deployment at 100% before continuing. Receipts proving the same migration identity was applied select version upload plus verified promotion for all later releases. A changed lifecycle identity is a new atomic boundary.

An `applying` or `outcome-unknown` receipt is a hard stop until the exact Cloudflare state is reconciled; never retry its release ID or infer lifecycle state. The atomic lifecycle migration is not reversible by reverting the Worker code. Canary validation still gates the automatic tenant batches, and every tenant uses the one central queue/timer without tenant-repository edits.
