# Fast, faithful design: replacement architecture

## Steps
- [ ] Establish an instrumented baseline and approve the replacement creative contract.
- [ ] Prepare the canonical runtime and a compact, complete design input before generation.
- [ ] Replace serial direction/locked-template realization with one Ada creative session.
- [ ] Expose the exact compiled candidate immediately through the existing workspace preview.
- [ ] Consolidate validation, repair, approval and publication around that candidate.
- [ ] Benchmark template-assisted and free composition, then deliver Astrid's autonomous replacement.
- [ ] Remove superseded orchestration and verify the complete owner journey.

## Status and decision

Owner approved implementation. This document authorizes implementing the replacement architecture, not production publication. It replaces the mandatory section-library-v3 realization restriction and the requirement for a separate expansive direction pass. The authoritative brand-composition-and-behavior-system implementation document must be reconciled with it; do not leave contradictory instructions active.

The product is a beautiful, business-specific website generated by Ada from confirmed intake, visible quickly in the owner's workspace, editable through canonical Payload fields, and published only after exact owner approval. Infrastructure exists to enable that journey, not to make the model perform an infrastructure project for every page.

Owner priority, clarified after review: first produce a beautiful, faithful design through a simpler and meaningfully faster workflow; optimize further afterward. Two minutes is not a deadline, acceptance condition, timeout, release blocker or reason to truncate creative work. Record elapsed time and eliminate demonstrated waste without sacrificing the result. Preserve larger confirmed experiences and report their actual timing honestly. The existing approximately twenty-minute product expectation remains a reporting obligation, not a reason to claim completion or silently drop requirements.

## 2. The replacement in one sentence

Prepare a working canonical website environment, give one Ada session the complete compact brief and actual assets, let it design the presentation, show its first compiled candidate immediately, and finish existing checks against that same candidate before enabling exact publication approval.

One workflow, not a new fast-path product beside the old product:

1. Confirmed intake and experience requirements become a compact, versioned input.
2. Host prepares the canonical Payload scaffold, dependencies, media and bindings.
3. Ada chooses one direction and authors the complete presentation in one session.
4. Existing build/preview machinery retains the source identity and serves it in the workspace.
5. Existing checks inspect that rendered candidate while the owner can see it.
6. Owner requests changes or approves the exact eligible candidate.
7. Existing release queue promotes the approved source/content identity to the registered Worker.

## 3. What remains fixed, and what becomes free

Keep fixed: confirmed facts and prohibited claims; selected assets and provenance; required locales; owner-required section/order/experience constraints; canonical schema/content ownership; stable editable field identity; tenant identity; approved dependencies; accessible/resting/reduced-motion behavior; immutable candidate identity; explicit approval; canonical release queue.

Free Ada to author: presentation JSX, responsive layout, spacing, typography, image geometry, composition, palette within owner constraints, and meaningful motion. A section's semantic identity does not force a fixed component or visual arrangement. Confirmed ordered content stays ordered unless the owner authorizes a change. If only an outcome is confirmed, do not invent a host-level layout restriction.

No schema, migration, auth, admin, secret, package-pin or runtime-config mutations by Ada. No duplicate content store or JSX business-copy literals. No host-authored candidate design. No silent missing-content fallback.

## 4. Compact input: information without the paperwork

Compile the existing intake and planning artifacts into one bounded view, not a second source of truth. The view references exact revision/hash and contains:

- business, audience, visitor objective and conversion destination;
- required sections, final copy or approved copy facts, locales and unknowns;
- approved media IDs plus usable local image evidence, dimensions and focal constraints;
- brand evidence and owner design preferences;
- every defining experience requirement, its observable result, responsive translation and reduced-motion equivalent;
- canonical content/binding interface and allowed presentation files;
- available design/motion capabilities and exact prepared dependencies.

Deduplicate repeated requirements and remove deployment prose, historical transcripts and full repository inventories from the creative prompt. Never omit copy or images from the designer's view just because runtime content must come from Payload. Read-only copy in model context is not a second runtime store.

Budget the common three-section input at roughly 6,000–10,000 text tokens excluding images; record actual size. Preserve all owner requirements when that target cannot fit and report why. Do not truncate requirements to meet the budget.

When the confirmed plan is already complete, do not plan it again. When it contains facts rather than final copy/composition, Ada supplies missing creative decisions in its same session. Before source edits, persist a concise creative delta in the existing planning artifact: thesis, section roles, media mapping, copy decisions and required behaviors. The host stages final copy through the existing Payload draft service, then returns the receipt to that same session. No separate planner, expanded behavior essay or second creative director.

## 5. Templates: optional acceleration, never a ceiling

Always reuse the technical starter: Next/Payload runtime, routing, media reader, editable bindings, Tailwind/PostCSS, approved motion dependencies and prepared package installation. 'From scratch' means new presentation inside this working runtime, never rebuilding CMS, auth, deployment or tooling.

Default initial experiment: free presentation composition with the prepared binding API. Compare it against optional template assistance using identical intake, model, dependencies and measurement.

A template may qualify as an accelerator only if it is already a complete, visibly coherent responsive composition, with appropriate no-image behavior, typography, image treatment and mobile translation. It must be easy to modify, not a frozen shell. Do not build a large template catalogue first. Audit what exists; fix or retire unusable primitives rather than calling them finished templates.

No model-driven catalogue search or extra template-selection stage. Supply at most a small relevant starting set with actual previews if benchmarking proves a benefit. Ada may reshape or ignore it. Do not assign industry-specific layouts in host code. Keep any selected template snapshot candidate-local and pinned; runtime overlays must never redesign existing customer sites.

The decision rule is measured owner-visible result and total time, not lines of code saved. If templates make the model fight CSS or adapter constraints, remove them from the default creative turn.

## 6. One session with a narrow job

The agent starts in a ready presentation workspace. It sees exact files and interfaces without discovering the whole repository. It inspects supplied assets, records only missing creative decisions, writes the page, and finishes. Layout, copy hierarchy, imagery and motion are solved together.

Move deterministic work out of its turn: package installation, Tailwind setup, canonical content staging, field-binding mechanics, metadata marker plumbing, Git snapshots and preview setup. Extend the existing shared adapter; do not introduce another content reader or framework. Ada selects stable entry IDs and semantic regions; host utilities derive editable/evidence attributes consistently.

Expose a small render-facing API over existing canonical records that preserves all entries and actions without flattening services, gallery and contact into the same HeroContent shape. Missing required data throws a clear error. This is an adapter over Payload, not a new schema or serialized content copy. Business content remains in Payload at runtime.

Use the configured model initially. Measure provider latency, input/cache/output/reasoning usage and tool execution separately. A model change requires explicit authorization and a controlled comparison; never hide an architectural failure with a silent substitution.

Avoid model-authored repeated typechecks, browser-server setup and package exploration. The host runs the existing check/build once per source revision and gives precise errors back if necessary. Do not run an identical check again without a change or unresolved failure.

## 7. Preview is an artifact, not a reward

Use the existing run, candidate SHA, Payload revision set, preview job and draft identities. No parallel preview store or approval path.

Once a compiled candidate loads, show it inside the real authenticated workspace with its current check state. A compiled-but-unchecked candidate is explicitly unapproved; publication controls are unavailable until existing eligibility requirements are satisfied. Visibility must not depend on final review-draft creation.

Project preview availability, check progress and publication eligibility as separate facts from existing durable records. Do not hide an available candidate because a newer attempt failed. Show the retained candidate and the current attempt/error distinctly. When a newer candidate becomes available, switch atomically with its exact source/content identity; never relabel an older iframe as the new result.

A restart reattaches to a valid existing preview or transparently rebuilds that exact source through the existing recovery path. Progress appears in place. Do not promise durable running processes across deployments without proving lifecycle support. Persist identity and recoverability, not a false ready flag.

Do not expose raw preview URLs as an alternative customer workflow. Release shared admin changes through its versioned package and canonical Worker rollout; backend projection alone does not satisfy visibility.

## 8. Checks and repairs: consolidate, do not multiply

Keep the existing build, content integrity, hydration, asset/module loading, responsive/accessibility and required behavior checks. One evidence collection over the exact owner preview should supply their shared browser observations rather than repeated independent renders where feasible. Retain read-only visual review of actual hydrated output; no new aesthetic scoring engine, taste gate or committee.

Checks run after first visibility and reuse the same immutable candidate and browser evidence. Exact module/asset failures remain failures. A motion signature must be exercised while it is visible, including mobile and reduced motion; source presence is insufficient.

One bounded repair opportunity for a specific implementation defect, in the same creative session when available, with concise observed evidence. A host delivery error is repaired in host code and the candidate rechecked; it must not trigger creative regeneration. A fundamentally wrong concept requires a deliberate new design attempt, not an endless cascade of repair children. The last inspectable candidate remains visible.

Owner criticism of design is input to Ada's next creative attempt, not permission for the coding agent to rewrite the page or introduce a new generic quality gate.

## 9. Approval and Worker publication

Investigate and fix Astrid's actual publication error independently using the exact failed request/response and current draft identity. Preserve its failed evidence. Do not send a real approve request as a diagnostic or bypass eligibility to get a successful release.

Approval binds exact source SHA, Payload document revisions, manifest and tenant. Source approval, content publication and deployment receipt must describe the same approved candidate. Existing compare-and-swap protections reject concurrent content changes. The canonical VPS queue remains the only deployment path.

The workspace must distinguish preview available, checks incomplete, approval available, publication queued, deploying, live and failed using existing durable state. A failed publish keeps the candidate visible and explains the actionable cause. No generic 'could not publish' where a safe structured error is available.

This plan does not treat the earlier unsuccessful publish click as authorization to publish a replacement design. The owner approves the new exact candidate. Verify the public Worker and fresh authenticated workspace after a passing release receipt before declaring it live.

## 10. Latency design and measurement

Measure admission, runtime prepared, first model response, first edit, source retained, preview reachable, owner iframe hydrated, checks complete, approval and deployment separately. Record model wait, tool execution, dependency preparation and build time without conflating wall time with CPU utilization or cost. Transcript cost estimates are not provider invoices.

Do not impose per-stage second budgets in this implementation. First eliminate the measured duplicate planning, repository discovery, model-authored plumbing and repeated builds. Record the resulting design quality and end-to-end elapsed time against the baseline. Once the result is good, optimize the largest measured remaining cost without changing its content or experience. Publish deployment is measured separately after approval. Keep existing operational timeout protections; neither shorten nor extend them merely to force a successful benchmark.

Prepare dependencies and immutable toolchain caches ahead of a design request using the existing canonical scaffold. Reuse package caches safely keyed by lockfile, runtime fingerprint and toolchain. Isolate tenant content/secrets and writable build outputs. Do not clone another full runtime per micro-step or invent a second build engine. Cold start must be visible and measured separately, not excluded from the owner journey.

If Next/Payload compilation dominates latency, profile that actual stage before changing architecture. Optimize reusable preparation and incremental work within the canonical builder; do not substitute a static mock or different renderer to claim speed.

## 13. Benchmark and acceptance

Then verify generality with a different visual identity and an interaction-heavy requirement. If an existing polished template is a credible alternative, compare it with free composition using the same configured model, brief and environment. Do not build a template catalogue to enable this comparison. Record all runs and failures, not only the best result. Repeat the selected approach once to expose obvious variability. Stop and analyze clear regressions rather than repeatedly regenerating until an attractive sample appears. Estimate cost before expanding the experiment and obtain approval if it exceeds established task spending authority.

Assess real desktop/mobile owner previews: visual hierarchy, purposeful images, typographic coherence, distinct section composition, complete content/actions, locale fidelity and required behavior. This is implementation evaluation with the owner, not a new production aesthetic gate. Do not measure beauty by source length, animation count or checklist claims.

Success requires:

- Ada generated the candidate from the exact confirmed intake without coding-agent design edits.
- The defined experience is visible and works in the actual workspace iframe, including reduced motion.
- All required copy/assets/locales/actions remain canonical and editable.
- First visible render and complete-check timings are recorded against the baseline, with eliminated work demonstrated. No two-minute threshold blocks an otherwise successful design. A run that remains slow is reported honestly and profiled after the design works.
- A failed follow-up/check/restart does not erase access to the retained candidate.
- Preview before approval and publication only after exact approval both work.
- The production Worker receives the exact approved identity through the queue; real authenticated verification follows release.
- The superseded generation path is removed from new-run execution, not merely bypassed with another conditional.

## 14. Coding-agent execution contract

This section turns the architecture into bounded implementation work. Do not implement the whole document as one broad rewrite. For each step, inspect its actual call sites, name the existing functions being changed and the obsolete branch being removed, add the focused regression, implement, and record real verification. Follow repository issue/PR coordination and required full-suite/package checks. A manager resolves code-level ambiguity from the repository; do not invent parallel abstractions or bounce routine implementation questions to the owner.

### A. Resolve authority and identify exact changes

Deliverable: a source map listing the live initial-homepage entry point, direction dispatch, content staging call, implementation dispatch, candidate finalization, preview projection and approval route. Include their actual symbols and callers, not just directory names. Trace Astrid's stored run through them. Record which mandatory-template instructions and branches will be deleted versus retained solely to read old candidates.

Acceptance: the canonical architecture and prompt instructions no longer simultaneously require creative freedom and prohibit structural edits. Existing pending drafts remain readable. No changes to an old candidate's source or content occur.

### B. Prepare the input and renderer contract

The compiled input is derived from existing records, never a new persistent business-content authority. It must carry intake identity/revision/hash; stable section and entry IDs; exact read-only copy by locale; media identity and usable image evidence; action labels/destinations; owner constraints and experience outcomes; allowed source files; and the existing renderer/binding interface. Include a requirement-to-input trace in test fixtures so prompt compaction cannot silently drop a requirement.

The render-facing helpers must resolve entries by stable ID, preserve their existing typed values, and produce the existing editable markers. They must support multiple images, paragraphs and actions independently. They must not return a forced hero-shaped object. Reuse existing types and binding functions; extend the shared adapter only where its current interface cannot express this. Business values are resolved at runtime from the exact Payload document supplied by the route.

Acceptance fixtures: a text-only section; a section with two images and two distinct links; two locales; missing required media; duplicate/missing entry identity; a stale content revision. Verify valid values and markers survive and invalid cases fail explicitly. Layout choice must remain with presentation JSX. Optional absent images must not create host-mandated image containers.

### C. Implement one session, with explicit resume semantics

Normal path: prepare runtime -> assemble compact input -> resume/create the run's existing Ada session -> persist any necessary creative delta -> stage/verify Payload draft -> continue that same session to author source -> retain candidate -> compile/preview. If final copy is already staged for the exact input, reuse its verified receipt rather than write it again. Stage through the existing application service and durable operation identity, not direct model database writes.

A complete confirmed plan bypasses a new direction request. An incomplete creative decision is supplied within the same session; it does not trigger an independent planner. Persist the session and staging receipts before continuing so interruption resumes from the earliest valid boundary. Do not promise exactly-once execution from a process-local flag: use existing durable idempotency and revision checks.

Acceptance: a mocked orchestration test proves one primary session identity, no independent native-direction dispatch for this new path, staging before source generation, no duplicate draft writes on resume, and retention of the resulting candidate. Prompt tests prove both complete requirement coverage and absence of locked-hero instructions. A real run must confirm the model actually receives usable images and copy, not only IDs or an assertion that assets were attached.

### D. Make visible preview independent of eligibility

Extend the existing workspace projection; do not add a second endpoint or preview database. Resolve the visible candidate using its run/SHA/content-revision identity. The shared admin embeds that exact compiled preview as soon as available and displays check progress separately.

Required cases: no candidate yet; compiled/checking; compiled/check failed; eligible/pending owner approval; failed follow-up with retained parent; newer candidate ready; restart/recovery; stale response arriving after selection changed. For each, assert which candidate is visible, which status is displayed and whether publication is permitted. A status refresh must never switch the iframe to mismatched source/content.

Acceptance: fresh authenticated owner browser shows a real hydrated candidate while checks are deliberately still running, then retains it after a check failure. Mobile and reduced-motion behavior are exercised there. The proper shared-admin package is released; backend-only success is insufficient.

### E. Keep failure handling small and causal

- Model/provider failure before source: preserve run/session evidence; show failure, do not manufacture a candidate or automatically switch providers.
- Build failure after source: retain source and build diagnostics; do not label it a compiled preview. One bounded Ada repair may address the specific failure.
- Preview transport/runtime failure: repair delivery and recheck the same SHA; do not regenerate design.
- Failed design requirement: retain visible result and precise evidence; one bounded fidelity repair, or an explicitly initiated new creative attempt when the concept is wrong.
- Stale Payload revision at approval: reject the exact approval safely and retain preview with an explanation; do not silently approve newer content.
- Queue/publication failure: preserve receipt and preview, expose the safe actionable error, and use the existing canonical recovery process.

Acceptance: tests prove these outcomes and that no failure automatically publishes, deletes the retained candidate, loops through unbounded repairs or creates a parallel recovery workflow. Diagnose Astrid's publication error from evidence before selecting its code fix.

### F. Demonstrate creative success, then optimize

First deliverable: Ada's new Astrid page in the actual workspace, with complete required content, intentional type hierarchy, purposeful imagery, coherent desktop/mobile composition and the specified experience. Assess actual screenshots and interactions against her brief; a completed plan, a large CSS file or added animation is not proof of beauty. Keep this assessment in the existing review/owner feedback process, not a new runtime score threshold.

If it is still generic or poor, inspect the exact input, generated composition and rendered output to locate the loss. Do not add another general design critic, hardcode Astrid's composition into shared code or hand-polish her generated source. Correct the generic creative boundary and let Ada generate again under an explicit attempt identity.

Only after that result works, optimize the largest measured delay. Change one source of overhead at a time, compare before/after using the same input and requirements, and retain visual/behavioral evidence. Do not trade away content, images, interaction, locales or rendering fidelity for a shorter timing.

### G. Definition of an implementation handoff

Each handoff names exact commits, changed contracts, removed branches, focused and required broader test results, and remaining limitations. End-to-end handoff additionally includes run/session ID, intake revision, candidate SHA, Payload revision identity, preview identity, actual owner-surface evidence, phase timings and publication state. An unavailable provider, lack of owner approval or unreleased admin package is reported explicitly; never replace it with fixture success.

The manager may not mark the architecture complete while the old mandatory-template path remains active for new runs, early preview is only backend data, or the replacement has not been autonomously generated and observed. Public release acceptance waits for owner approval; absence of that approval does not prevent delivering and reviewing the new design.
