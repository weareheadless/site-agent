## Read-only native timeout, spend, and resume audit

- `run_opencode_turn` (`hands/opencode_runner.py:3999+`) uses `timeout_seconds` or `builder.timeout_seconds` (default 1800), starts a watchdog, terminates the process on timeout, and raises `RunnerError`. `native_build` calls it with the execution config, passes `memory` for accounting, and does not provide a pre-call spend authorization or validation-repair budget.
- OpenCode usage/cost is extracted from emitted events and, in `run_opencode_turn`'s `record_usage()` finalizer, written to `Memory.log_llm_cost` as `origin="internal_builder"` after the turn. This is accounting, not a pre-call cap. `core.llm.LLMClient._check_budget()` checks the rolling `llm_spend(since_hours=24)` before that client's `chat`/`chat_tools` requests. Native `run_opencode_turn` does not use that client or call `_check_budget`; its private guard cannot be treated as enforcement for this separate invocation. Whether an existing policy can be safely shared is unresolved; no budget subsystem or policy is proposed here.
- Durable restart handling is in `DesignJobWorker._recover_queued` (`application/design_jobs.py:392+`): it re-enqueues created/assessing/planning runs with a queued event, and planning runs with persisted `build_request` and `build_target`; otherwise those planning runs are marked interrupted. `_run` rehydrates those values and calls `DesignService.execute_build`. A thrown error is transitioned to `FAILED` (`_run`, around lines 682–697), and failed runs are not selected by `_recover_queued`. The planning payload is the build request/target, not a persisted native typed-plan repair checkpoint. Thus these existing resume/durable boundaries are useful context, but do not themselves resume a failed native parse or establish safe retry identity/deduplication.
