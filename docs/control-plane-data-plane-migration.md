# Control plane and data plane: one workspace, one build contract

**Status:** active implementation plan, 2026-11-08
**Supersedes:** the "Deferred: platform-hosted admin" section of
`docs/admin-shared-runtime-migration.md`.
**Does not change:** the tenant Worker's public site, Payload CMS, tenant data,
domain, or release approval contract.

## Why this exists

The current shared runtime is not a package. It is a source overlay: at release
time the VPS copies 45 files and two directories (`src/admin`,
`src/components/admin`) into a disposable build of each tenant repository. The
owner workspace is a Payload custom view inside every tenant Worker.

That solved the old admin package-version ceremony, but it created a worse
coupling:

- Every admin change rebuilds and redeploys every tenant Worker.
- The admin and the tenant site share one Next build, one `tsconfig`, one set of
  generated inputs, and two independent build pipelines.
- Release and compiled preview have separate step lists. A new generated input
  can be added to one and not the other; the committed-route inventory did
  exactly that and broke design previews.
- A tenant frontend change can break the owner admin, and an admin change can
  fail on a tenant's site code.
- The workspace only treats Payload documents as editable context, so a site
  whose pages are committed Next routes looks empty to the owner.

With three live tenants this is already expensive. With fifty it is
unsustainable. The deferral in `admin-shared-runtime-migration.md` is now the
bottleneck, so this plan un-defers the physical separation.

## Target topology

```text
Owner
  -> helloada.app                     control plane
       owner auth, project selector, workspace,
       Growth, Messages, Gallery, Activity,
       previews, approvals, releases
  -> api.helloada.app                 site-agent API
       tenants, jobs, drafts, content, growth, releases

  -> tenant.com                       data plane, one Worker per site
       public frontend (Next/Payload or static)
       Payload API + raw Payload admin (optional)
       preview alias
       health, mail, forms
```

The owner workspace is no longer built into a tenant Worker. It is one app on
the control plane. The tenant Worker keeps the public site, Payload and the
runtime surfaces that need to be same-origin with the site.

## UX invariants

These must stay true throughout the migration:

1. Website visitors see the same site, domain and content.
2. A tenant that uses Payload keeps its own Payload CMS, D1/R2, media, products,
   users and permissions.
3. Tenant data is isolated. Only platform code is shared.
4. The owner workspace keeps the same screens and actions; it moves to
   `helloada.app` and uses the HelloAda login.
5. Preview stays an iframe of the tenant's real preview alias.
6. The tenant Payload admin stays available at the tenant domain for advanced
   CMS work, with its own login.

## Contracts

### Workspace contract

A typed, versioned API between the control plane and each tenant. It covers:

- site identity and route inventory (Payload documents plus committed pages)
- documents, drafts, revisions and publication
- media
- preview plan, preview URL and preview status
- Growth, Messages, Gallery and Activity
- source preview and design candidates

The existing `/v1/workspace/*` application surface is the starting point. The
control plane authenticates with its server-only token and resolves the tenant
explicitly; the browser never holds a tenant or service token.

### Site build contract

One module, used by both release and compiled preview:

```text
inputs   tenant checkout, pinned package versions, runtime fingerprint
steps    overlay, generate contract + route inventory, typecheck, build
outputs  artifact hash, manifest, route inventory, preview runtime
```

Rules:

- No build input may be generated by only one path.
- The presentation inventory is a site build output. It is not a file the
  admin build imports.
- Preview and release run the same generator with the same inputs.
- A parity test builds a fixture through both entry points and compares every
  input and output.

### Package boundaries

| Package | Owns | Consumed by |
| --- | --- | --- |
| `@weareheadless/helloada-payload-core` | schema, content contract, bindings, route resolver | every tenant site |
| `@weareheadless/helloada-site-runtime` | health, preview alias, workspace bridge, mail hooks | every tenant Worker |
| `@weareheadless/helloada-workspace-contract` | typed workspace API and shared route/preview types | control plane and site runtime |
| control-plane app | owner workspace UI and API proxy | one deployment |

Tenant repositories contain design, frontend code, content, assets and
`helloada.config.ts`. They do not contain owner admin source.

## Migration phases

### Phase 0 — containment

- Freeze shared-runtime overlay changes and tenant rollouts except security or
  data-loss fixes.
- Restore compiled previews with the same generator the release uses. This is
  Phase 1 work, not a separate patch.
- Do not migrate more tenants until Phase 1 exits.

Exit: a design/source preview compiles after an admin or generated-input
change, and the public sites are unchanged.

### Phase 1 — one site build (implemented here)

- Move the contract generator into the packaged template
  (`templates/next-payload/scripts/generate-payload-contract.mjs`).
- One inventory module, one generator, one fingerprint entry set.
- Compiled preview runs the generator after dependencies and before typecheck,
  then rewrites Wrangler for its isolated local bindings.
- Release runs the same generator before typecheck.
- Add a parity/ordering test.

Exit: preview and release share the generated inputs; changing a shared file
cannot break only one path.

### Phase 2 — move the owner workspace to the control plane

1. Add a control-plane auth path to the workspace API: server-only token plus an
   explicit tenant identity. The browser never sees it.
2. Add a central site snapshot endpoint: site identity, committed routes from
   the build inventory, and Payload routes/documents through the tenant
   workspace gateway.
3. Add `/websites/[id]/workspace` to the HelloAda app, reusing the existing
   workspace components and styles.
4. Proxy browser requests through the HelloAda app server to the site-agent
   workspace API. No tenant service token in the browser.
5. Keep the tenant preview alias in the iframe and the tenant Payload admin as
   an advanced link.
6. Canary inmersion.

Exit: the owner opens the workspace on `helloada.app`, sees the site, routes,
preview, Growth, Messages and approvals; an admin-only change requires no
tenant Worker rebuild.

### Phase 3 — shrink the tenant runtime

- Extract health, preview, workspace bridge, forms and mail into
  `helloada-site-runtime`.
- Remove `src/admin` and `src/components/admin` from the tenant template and
  overlay.
- Remove the owner workspace from the tenant Payload admin import map.
- Keep Payload's raw admin.

Exit: a tenant build contains no owner admin code; the overlay is reduced to
the site runtime or deleted.

### Phase 4 — migrate and delete the old path

- Migrate inmersion, casamigo, oceanicvibes, then the blocked tenants.
- Remove the fingerprint fan-out for admin changes.
- Delete the overlay, the preview-specific overlay and the old admin custom
  view.

Exit: one admin deployment for all tenants; a tenant build happens only when
that tenant's site or a pinned package changes.

## Rollback

- Phase 1 is source-only and reversible by reverting the build-contract commit;
  no tenant data or schema changes.
- Phase 2 keeps the tenant `/admin` view in place until the canary passes. The
  control-plane workspace is additive.
- Phase 3 removes the tenant admin only after the canary and a rollback release
  are proven.
- No phase changes tenant content, schema, D1, R2 or domains.

## Risks

- **Auth.** The control-plane token is powerful. It stays server-side, and the
  HelloAda app checks website ownership before proxying.
- **Payload admin separation.** Payload's raw admin remains tenant-local; the
  owner workspace is a separate app. Do not try to run Payload's admin for many
  tenants in one deployment.
- **Custom schema.** Tenant-specific collection shapes are not supported today.
  If a real tenant needs one, add an explicit extension mechanism to the core
  package; do not fork the schema.
- **Preview fidelity.** Keep the tenant preview alias, built by the single site
  build. A central renderer would drift.

## Open decisions

1. Workspace host: `helloada.app/websites/<id>/workspace` (recommended) versus a
   separate `workspace.helloada.app`.
2. Payload admin policy: keep it as an advanced tenant surface (recommended) or
   hide it behind a setting.
3. Tenant-specific schema: not needed until a tenant proves it; then an explicit
   core extension.
4. Preview: tenant alias in an iframe (recommended).

## Current implementation status

- Phase 1: implemented in this change. The generator lives in the packaged
  template; preview and release call it; the duplicate root script is removed.
- Phase 0: contained by Phase 1; the compiled-preview path now generates the
  same inputs as release.
- Phase 2: implemented for the canary. The control plane has a trusted
  workspace gateway (`/v1/control-plane/websites/{tenant}/workspace/...`) that
  injects the tenant workspace token server-side, and a `workspace/site`
  snapshot endpoint that reads the Worker's canonical site snapshot. The tenant
  API keeps its own auth contract; the control token is not a workspace service
  token.
- The Worker bridge also accepts the tenant workspace token with an explicit
  HelloAda owner subject
  (`/v1/control-plane/websites/{tenant}/worker/...`). The Worker links that
  subject to the same durable Payload owner the signed handoff creates, so the
  control plane gets the same access checks and audit identity without a
  browser session or a second user model.
- The HelloAda app serves `/websites/<id>/workspace` and proxies browser calls
  through its own authenticated server route. The ported workspace UI reads the
  tenant's own site configuration from the snapshot (locales, modules, preview
  mount) instead of guessing it.
- Known limitation of the canary: the preview is a cross-origin iframe of the
  tenant alias, so direct in-preview element selection cannot read the frame.
  The panel editor remains available. A same-origin preview bridge is Phase 3
  work, not a reason to proxy the whole site through the control plane.
